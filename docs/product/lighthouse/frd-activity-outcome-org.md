# 燈塔「動態 / 成果 / 組織設定」FRD

> 2026-09-11 從 Google Doc 同步：https://docs.google.com/document/d/1q5m6UjCUv9xKkzbRcSXzhz3Rzg_mpU9iuvqLdh212gU/
> 對應 issue：daodaoedu/daodao#189；原型：`prototype/lighthouse-admin-preview` 分支的 `docs/product/admin/prototypes/lighthouse-admin-prototype/`

## 1. Purpose 目的

本文件定義燈塔管理端「動態」、「成果」與「組織設定」三個模組的功能需求與測試重點，作為產品、設計、工程與 QA 對齊目前原型行為的依據。

三個模組分別支援管理者／主持人：觀察場次近期的打卡、留言與學習節奏變化；將實踐紀錄整理為可回顧與匯出的成果證據；以及維護組織對外資訊、查看管理成員與設定成果摘要使用的 AI API key。

## 2. Scope 範圍

### 2.1 In Scope

- 動態：場次內「動態」頁籤、統計卡、最近 7 天查詢範圍、關鍵字／類型／實踐／有文字內容篩選、動態列表、排序、空狀態與動態明細。
- 成果：場次內「成果」頁籤、成果概況、AI 場次成果摘要、AI 模式切換、摘要產生／重新產生、摘要人工編輯、實踐成果、參與者進度與匯出入口。
- 組織設定：組織資訊表單、組織成員顯示與目前限制、組織層級 AI API key 輸入、狀態與 prototype 連線測試，以及此設定與成果摘要 AI 模式的關聯。

### 2.2 Out of Scope / Prototype 限制

- 其他場次管理頁籤（例如儀表板、名單、今日焦點）、系列與場次、模板庫、封存等，不在本文件範圍。
- 組織資訊的「儲存」按鈕目前未綁定 onClick；原型僅證明欄位與操作入口存在，不證明資料會寫入後端或跨工作階段保存。
- 組織成員的新增 Email 欄位與新增按鈕為 disabled，畫面明確標示即將推出；既有成員旁的「移除」按鈕也未綁定事件，本版不視為可驗證的成員管理功能。
- AI API key 的「測試連線」為 prototype demo：只依欄位是否非空回傳示範成功／提示訊息，未證明真實第三方 API 驗證、加密儲存、金鑰生命週期或權限控管。
- 成果頁的場次 PDF 為既有下載連結；程式碼未呈現即時產檔流程。學員成果紀錄匯出按鈕為 disabled 並標示 coming soon。
- 成果概況、實踐成果與參與者進度目前以示範資料呈現；FRD 將其視為應顯示的資料結構，不推定原型已完成後端統計計算。

## 3. Functional Requirements 功能需求

### 3.1 動態

#### FR-ACT-01｜頁籤入口與頁面目的

- 原型已確認：場次管理頁包含「動態」頁籤；使用者切換至該頁籤後，畫面顯示動態頁說明、統計卡、篩選列、動態列表與明細入口。
- 正式產品需求：管理者需能在指定場次內查看近期打卡、留言回應與學習節奏變化；系統需依使用者權限與場次識別載入對應資料，無權限或場次不存在時需顯示明確狀態。

#### FR-ACT-02｜動態統計卡

- 原型已確認：動態頁顯示「打卡」、「留言與回應」、「節奏變化」、「全部學習動態」四張統計卡；數字依目前篩選後的動態資料列計算；「節奏變化」與「全部學習動態」旁提供 i 說明提示。
- 正式產品需求：統計卡需與目前查詢條件同步更新，且四張卡都需套用相同場次、權限、日期區間、類型、實踐、關鍵字與文字內容篩選；排除已刪除、封存、無權限或無效資料。
  - 打卡需使用打卡紀錄資料，至少包含 activity_id、session_id、member_id/member_name、practice_id/practice_name、occurred_at、content/detail、has_text、status，計算符合篩選條件且 type=打卡 的唯一筆數。
  - 留言與回應需使用留言／回應資料，至少包含 comment_id/reply_id、session_id、actor/member、practice_id/practice_name、occurred_at、content、target_activity_id、status，計算符合篩選條件的唯一留言與回應筆數。
  - 節奏變化需使用系統產生或後端計算的節奏事件資料，至少包含 rhythm_event_id、session_id、member_id、practice_id、event_type、event_at、basis_metrics（例如 quiet_days、streak_count、last_checkin_at、goal_change）、summary、status，計算符合篩選條件且 event_type 屬於正式定義範圍的唯一事件數。
  - 全部學習動態需以標準化 activity feed 作為資料來源，將打卡、留言／回應與節奏事件合併後依 activity_id + activity_type 去重，計算符合目前篩選條件的總筆數；說明提示需支援滑鼠 hover 與鍵盤焦點。

#### FR-ACT-03｜期間篩選與範圍防呆

- 原型已確認：動態頁提供起始日與結束日輸入；原型以固定 min/max 日期限制最近 7 天範圍；若起始日晚於結束日，原型會自動整理為由早到晚；列表只保留日期落在區間內的資料。
- 正式產品需求：以場次所屬組織／場次設定的 timezone 作為最近 7 天基準；若未設定，預設 Asia/Taipei。查詢區間包含場次時區的今天與往前 6 個完整日曆日；伺服器端負責換算查詢起訖時間，前端顯示使用者可理解的日期範圍。

#### FR-ACT-04｜關鍵字搜尋

- 原型已確認：搜尋字串會 trim 後轉小寫，並比對成員、實踐、摘要、meta 與類型；目前不搜尋 detail 詳細內容；搜尋條件與日期、類型、實踐、文字內容篩選以 AND 合併。
- 正式產品需求：支援全文搜尋，搜尋範圍至少應涵蓋動態列表可見欄位，並需確認是否包含 detail 詳細內容；搜尋結果需與其他篩選條件及統計卡同步。

#### FR-ACT-05｜類型、實踐與文字內容篩選

- 原型已確認：動態頁提供類型篩選（全部類型、打卡、留言、節奏變化）、實踐篩選（全部實踐與兩個示範實踐）與「只看有文字內容」checkbox；所有條件以 AND 套用。
- 正式產品需求：實踐選項需由目前場次的實踐清單載入；篩選後無資料時需顯示空狀態，解除條件後列表與統計需即時恢復。

#### FR-ACT-06｜動態列表與排序

- 原型已確認：動態列表顯示時間、類型、成員、實踐與摘要；資料依日期由新到舊排序，同一天內依時間由晚到早排序，並以日期分段。
- 正式產品需求：大量資料情境下需要分頁；排序規則需在跨頁資料中保持一致，列表筆數與統計卡需反映目前查詢結果。

#### FR-ACT-07｜動態明細

- 原型已確認：使用者點擊列表摘要可開啟單筆動態明細；明細顯示日期時間、成員、實踐、類型與 detail，並可透過右上關閉或遮罩關閉。
- 正式產品需求：支援從列表開啟單筆動態明細；若需以連結直接開啟指定動態，需定義深連結格式、無權限、資料不存在與載入失敗狀態。

#### FR-ACT-08｜空結果與載入狀態

- 原型已確認：當篩選後無資料時，列表顯示「這個篩選條件下沒有動態。」；原型未區分尚未載入、載入失敗與查無資料。
- 正式產品需求：需區分查無資料、資料載入中與資料載入失敗狀態；載入失敗需提供可理解訊息與重試方式，且不得殘留上一組查詢結果。

### 3.2 成果

#### FR-OUT-01｜成果概況

- 原型已確認：成果頁固定顯示四張成果概況卡：參與人數、啟動實踐、總打卡數、留言與回應；原型不進行後端統計計算。
- 正式產品需求：由正式場次資料計算並顯示參與人數、啟動實踐、總打卡數、留言與回應。場次尚未結束或尚無成果資料時，需顯示尚未產生成果的狀態；若已有部分資料，需標示為進行中資料，不可呈現為最終成果。

#### FR-OUT-02｜AI 使用模式

- 原型已確認：成果摘要區可在「平台 AI」與「自己的 AI API」之間切換；若選擇自己的 AI API 且 API key 為空，畫面顯示需先到組織設定完成設定的提醒。
- 正式產品需求：支援平台 AI 與組織自帶 AI API 兩種模式；可使用的模式需依組織設定、使用者權限與 key 狀態決定，並需定義 AI 用量控管。

#### FR-OUT-03｜產生／重新產生 AI 摘要

- 原型已確認：點擊「產生 AI 摘要」後，平台 AI 或非空自帶 API 狀態會顯示固定示範摘要；若自己的 AI API 未設定，原型不產生摘要；產生後按鈕文字改為「重新產生 AI 摘要」。
- 正式產品需求：以場次打卡紀錄與留言回應作為摘要資料來源，定義送出給 AI 的資料範圍、摘要 prompt、產生失敗、逾時、額度不足與內容安全處理流程；重新產生摘要需明確處理是否覆蓋既有草稿。

#### FR-OUT-04｜摘要人工編輯

- 原型已確認：使用者可點擊「編輯摘要」進入 textarea；取消不保存修改，儲存會以輸入內容更新摘要；原型允許儲存空字串。
- 正式產品需求：禁止空白摘要；儲存摘要需寫入正式資料來源，並需定義版本紀錄、審核狀態與最後編輯者／時間等資訊。

#### FR-OUT-05｜實踐成果

- 原型已確認：成果頁顯示「實踐成果」區塊，欄位包含實踐、參與、啟動、完成、打卡、留言/回應；目前為固定示範列，並標示此區不需要 AI。
- 正式產品需求：依場次資料計算各實踐成果；資料來源需至少涵蓋場次實踐清單、參與者/實踐關聯、打卡紀錄與留言/回應紀錄。各欄位需有一致計算公式，並排除已刪除或無效資料。

#### FR-OUT-06｜依參與者查看進度

- 原型已確認：成果頁顯示「依參與者查看進度」，欄位包含參與者、實踐、實踐進度、打卡完成、回應、最後動態；進度以完成數/目標數與百分比呈現，並說明此功能不是評分。
- 正式產品需求：依參與者與實踐顯示進度；完成數、目標數、完成率、打卡完成、回應與最後動態需有明確計算規則。進度不得作為評分，需用於理解完成步驟與學習證據。

#### FR-OUT-07｜匯出

- 原型已確認：成果頁提供「匯出場次成果報告」PDF 入口，連到既有 session-outcome-report.pdf；「匯出學員成果紀錄」按鈕為 disabled 並標示 coming soon。
- 正式產品需求：即時依目前場次資料產生 PDF，內容包含場次基本資訊、成果概況、AI 成果摘要、實踐成果與參與者進度；報告需依場次狀態標示「進行中資料」或「最終成果報告」。檔名規則為「場次名稱_成果報告_YYYYMMDD.pdf」，重複產生時需有固定版本規則。匯出權限限於可管理該場次的使用者。

#### FR-OUT-08｜自己的 AI API 與組織設定

- 原型已確認：成果頁與組織設定共用同一個 aiApiKey state；自帶 API 模式下，空 key 會阻擋摘要產生並顯示提醒，非空 key 允許原型示範摘要流程。
- 正式產品需求：以組織層級 API key 狀態控制成果頁自帶 API 模式可用性；若 key 未設定、無效、已停用或使用者無權限，需禁止產生摘要並顯示清楚提示。

## 4. Test Points 測試重點

### 4.1 動態

- TP-ACT-01｜頁籤與基本顯示：切換至「動態」後，確認說明文字、四張統計卡、篩選列與列表均顯示；切換其他場次頁籤後不應繼續顯示動態內容。
- TP-ACT-02｜日期邊界與反向區間：測試最小日、最大日、超出可選範圍、起始日晚於結束日；確認值會被限制在允許範圍，反向區間會自動整理為由早到晚。
- TP-ACT-03｜關鍵字搜尋欄位：分別用成員、實踐、摘要、meta、類型中的文字搜尋，應可命中；只存在於 detail 詳細內容中的關鍵字不應因目前原型邏輯而命中。
- TP-ACT-04｜組合篩選：同時套用期間＋類型＋實踐＋只看有文字內容＋關鍵字，確認結果符合所有條件；逐一解除條件後，筆數應相應恢復。
- TP-ACT-05｜排序：確認跨日由新到舊；同一天內由時間晚到早。
- TP-ACT-06｜統計卡：變更篩選條件後確認四張卡與列表筆數同步更新；確認四張卡數字分別符合目前篩選結果；確認「節奏變化」與「全部學習動態」的說明 icon 可透過 hover／focus 顯示正確文案。
- TP-ACT-07｜明細開關：點擊摘要後確認明細日期時間、成員、實踐、類型與詳細內容正確；測試右上關閉與遮罩關閉。
- TP-ACT-08｜無結果：設定無符合資料的組合條件，確認顯示指定空狀態訊息且不殘留上一組資料。

### 4.2 成果

- TP-OUT-01｜成果概況與結構化資料：確認四個成果概況卡、實踐成果欄位、參與者進度欄位皆可正常呈現；不將固定示範值視為後端計算驗證。
- TP-OUT-02｜平台 AI：AI 使用選擇平台 AI，按「產生 AI 摘要」，確認摘要與狀態更新，按鈕文字改為「重新產生 AI 摘要」。
- TP-OUT-03｜自己的 AI API／無 key：清空組織 API key，成果頁選自己的 AI API；確認顯示提醒，按產生摘要後不應產生新的 AI 草稿。
- TP-OUT-04｜自己的 AI API／有 key：輸入非空 API key 後選自己的 AI API，確認提醒消失，可產生摘要。
- TP-OUT-05｜編輯、取消與儲存：進入摘要編輯後修改文字；按取消應保留原摘要，重新進入編輯應從已儲存摘要開始；按儲存後新文字應顯示於檢視狀態。另測試空白摘要的行為。
- TP-OUT-06｜PDF 匯出：點擊「匯出場次成果報告」確認為 PDF 下載入口且下載檔名設定正確。
- TP-OUT-07｜學員成果匯出 Coming soon：確認「匯出學員成果紀錄」保持 disabled、不可點擊，並清楚標示 coming soon。

### 4.3 組織設定

- TP-ORG-01｜組織資訊 UI：確認組織名稱、組織簡介、外部連結與儲存控制顯示且欄位可編輯。
- TP-ORG-02｜成員顯示與限制：確認既有成員名稱與角色可見；新增 Email 欄位與新增按鈕為 disabled，並顯示即將推出說明。移除按鈕只驗證 UI 存在。
- TP-ORG-03｜API key 空值：API key 為空時狀態應為「尚未設定」；按測試連線應提示先輸入 API key。
- TP-ORG-04｜API key 非空：輸入任意非空字串後狀態應為「已設定」；按測試連線顯示成功訊息。輸入修改後，上一筆連線狀態應被清除。
- TP-ORG-05｜密碼欄位：確認 API key input 為 password 類型，畫面不直接顯示明碼。
- TP-ORG-06｜與成果頁同步：先以空 key 選自己的 AI API 驗證成果頁阻擋，再輸入非空 key 驗證成果頁可繼續摘要流程，確認兩處狀態一致。

### 4.4 建議列為產品確認事項

- 「節奏變化」的正式判定規則需產品確認，例如安靜／停滯後重新打卡、連續打卡里程碑、目標調整等事件是否全部列入。
- 組織資訊儲存、成員移除／新增、AI API key 真實保存與權限模型，正式版本需另補 API、錯誤狀態與持久化規格。
- 成果頁固定示範統計應由哪些資料來源與計算規則產生，以及 PDF 是即時產生、預先產生或版本化下載，原型尚未定義。
- AI 摘要是否允許空白儲存、產生失敗／逾時／額度不足如何處理，以及自己的 API 驗證失敗時的錯誤流程，原型尚未定義。
