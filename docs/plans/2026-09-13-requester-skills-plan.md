# 給需求提出者使用的 Skill：實作規劃

日期：2026-09-13。狀態：規劃完成，正式改版與情境驗證待實作。

本文件彙整本次對話的最新決策，作為後續實作依據，優先於先前規劃草稿中較繁重的欄位與角色設計。本次只新增規劃，不建立 Issue、不變更看板、不發布文件或啟動開發。先前已局部修改 prd-generation／product-status-check，但仍有舊規則尚待整合，不能視為本計畫已實作。

後續實查補充：已從 Issue #150、#171、#184、#189 讀取現有 Google 文件與 POC 索引，詳見[來源與格式盤點](2026-09-13-issue-source-format-audit.md)。既有 FRD 使用 Purpose／Scope／FR-*／TP-*／待確認事項；skill 應保留此結構與編號。新來源可只有開發分支，不強迫另補 PRD、FRD、POC 三件套。

最新建議：新需求統一產出一份 PRD，包含功能細節與驗收，不另外要求 FRD。大型 PRD 可按功能拆章節或連結子 PRD，維持同一種文件概念。既有 FRD 繼續作有效來源，保留其 FR／TP，不為改名重寫；技術設計、實作計畫、驗收結果分別由開發文件承接。

## 1. 使用者體驗

給寫需求的人使用，包括 PM、設計師或任何提出問題的人。使用者不需要懂 repository、API、根因、OpenSpec、SHA 或開發 phase。

**使用者描述 → skill 查現況 → 整理草稿 → 確認關鍵問題 → 交付可讀需求。**

- 不要求從空白表格逐格填寫。使用者只需要描述、選擇、修正與確認。
- 不填固定負責人；需求與驗收通常是同一角色。開發指派沿用 Issue。
- 所有工程調查與跨 repo 分流由 skill／開發處理，查到的限制翻成產品語言。
- 需求可以改變現況；查 codebase 是避免誤解，不是要求使用者接受既有缺陷。
- 每次問一兩個影響最大的問題，已有答案不重問；未回答的決策不能由 AI 自動定案。
- 模板供 AI 整理，也供人直接閱讀／編輯，不要求所有協作者安裝 agent。

## 2. 使用入口與內部分工

只呈現兩個日常入口，沿用既有 skill 名稱，避免再加一套總控 skill。

| 使用者說法 | Skill | 使用者得到什麼 |
|---|---|---|
| 「幫我整理需求」「我想改善這個流程」 | prd-generation | 一份符合現況、標明改動與待決問題的需求草稿 |
| 「幫我看這份 PRD」「這個規則要改」 | prd-generation | 原文件的缺漏／差異與更新稿，保留原決策和 AC |
| 「這裡有 bug」「這個畫面不對」 | file-bug-issue | 清楚的通報草稿、已知現況與待查事項 |
| 「用這份需求開卡」 | gh-card | 依已確認內容建立或更新授權範圍的卡片 |
| 「這功能現在做了嗎」 | product-status-check（亦供前兩者內部使用） | 有證據的現況與限制，不要求使用者選 repo |

不要把所有功能建立成必學指令。自然語言觸發為主；Codex 提供薄入口引用同一份 canonical skill，不複製規則。只說「幫我整理」就停在草稿；發布必須有相應授權，內容確認不等於派工授權。

## 3. 需求整理的完整對話流程

### 來源辨識：Issue、文件、POC、開發分支都可開始

- 從 Issue body 與相關 comments 取得直接關聯的文件／POC／branch／PR，區分需求基準、補充決策與開發驗收報告，不能把所有連結都當需求。
- 已有 FRD 就沿用 Purpose／Scope／Functional Requirements／Test Points／待確認事項；保留 FR-*、TP-*，直接作需求與驗收參照，不再強制改編 AC-*。
- 有產品框架但不叫 PRD 時，依實際內容辨認其目標／範圍用途，不改名或假設是一份正式核准 PRD。
- 有文件＋POC＋分支時先比對差異。沒有一種來源自動永遠勝出；以使用者對本次範圍明確確認的決策為準，有衝突才補問。
- 只有 branch／PR 時，由工具解析 repo、ref 與固定 head SHA；比較 PR target 或明確 base／merge-base，記錄基準理由與差異。分支名稱不代表已部署，也不自動代表全部差異都在本次需求範圍。
- 分別讀參考分支與實際目標 codebase：前者可能是要做成的樣子，後者是目前基礎。不能只讀參考分支後把它叫作現況，或把落後 main 的舊碼當本次變更。
- 先唯讀查 diff、相關文件與程式；需要觀察互動才在隔離環境依適用流程啟動。未啟動就只報靜態推論，不宣稱畫面或操作已驗證。
- 從 branch 整理「可觀察畫面／流程」「stub／mock／未接線」「需確認的產品規則」；seed、localStorage、固定 AI 摘要與非空輸入檢查不能當正式資料／服務契約。
- branch 更新時對照舊／新 head，更新受影響 FR／TP 與決策，不悄悄換驗收基準；ref 消失時保留已讀版本證據並明列無法刷新。

提出者看到的交付是可讀需求摘要與關鍵問題；SHA、來源修訂、檔案與 diff 放附錄，由工具維護，不新增技術必填欄位。

### A. 接受想法，先定位問題

接受一句話、使用案例、圖片或既有文件。先辨認使用者、入口、遇到的問題與希望結果。範例：「共同挑戰很亂」尚無法定位時，問「你是指找新挑戰的頁面，還是查看自己已加入挑戰的頁面？」不要一次丟十題。

只在有必要時詢問資訊；明確的小改動可直接查核並起草。圖片需要實際讀取，文件連結需要讀內容，讀不到就說限制，不猜圖片或文件寫了什麼。

### B. 查 codebase 與現有需求

由 skill 根據頁面與功能定位相關 checkout，確認 revision 及相關未提交差異。讀既有 PRD／FRD、設計及實際程式，沿適用的頁面、資料流、權限／規則與測試追蹤。只查足以判斷本次需求的範圍。

向提出者只說三件事：現在怎麼運作、期待會改變什麼、哪些地方需要確認。檔案／版本／查核證據放開發附錄或本地 evidence 檔。

證據分開：程式存在、指定測試通過、指定環境已部署、指定操作實際可用。codebase 的行為與使用者畫面不同時保留兩者，查版本／環境差異，不直接說使用者看錯。

若提出者的工具無法讀 repo，仍產草稿並標「現況待查核」；把待查範圍交給可存取的人／agent。不要求提出者貼原始碼或設定開發環境，也不宣稱已可開發。

### C. 先給草稿，再確認差異

無既有格式時預設整理一份 PRD，涵蓋五個內容區塊（第 5 節）；有現有 FRD 則沿用其結構與 FR／TP。只有分支也可以先整理需求摘要，不要求為了命名另生多份文件。清楚區分使用者已確認、程式查得、AI 建議與未知。不要憑空設定排序、上限、權限或預設值。

流程以使用者操作描述：前置狀態 → 動作 → 系統回應 → 下一步／完成；不是要求提出者教 AI 如何寫程式。不同頁面、角色、資料範圍要分清楚，例外只寫與本次有關的情境。

問句帶現況和影響。例如（假設查核結果如此，非本專案已確認事實）：「目前個人頁包含已結束項目。你希望保留並分類，還是預設只看進行中的項目？後者會讓已結束項目需要另外入口。」

### D. 補洞與確認

按影響檢查範圍、主流程、資料可見範圍、設計狀態、取消／錯誤、既有資料及驗收。只把需要產品選擇的問題交給提出者；實作方式由開發附錄處理。

逐輪更新同一份草稿，保留穩定 AC。若使用者轉向，修正範圍並記錄差異，不要求從頭重填。未回答的問題保持待確認；無關部分可繼續整理。

文件狀態用白話：「草稿」「待確認」「需求已確認，待開發評估」。最後一種表示提出者確認了內容，不代表工程可行性、時程或正式 Ready 已核准。若現況未查核，明列「現況待查核」，不能隱藏在已確認標記下。

### E. 交付

顯示文件位置與短摘要：要改什麼、已確認什麼、還缺什麼。接續動作使用者已授權就執行；未要求發布則保留草稿，不額外提示複雜的工程流程。

已有 Google Docs／既有文件就沿用其位置與決策，依當次授權編輯；無遠端寫入授權時提供本地修訂稿。沒有文件時先存本地 Markdown。跨工具自動同步不屬本次能力，不建立第二份無人維護的權威來源。

## 4. Bug 通報流程

1. 接受自然語言或圖片，先整理「在哪裡、做了什麼、實際結果、預期結果」。使用者不知道預期就標「待確認」，不立即判 bug。
2. 缺少重現資訊時問具體操作或發生情境；版本、瀏覽器、頻率只問有助於調查且對方知道的資訊，未知可先通報。
3. Skill 查相關程式、需求與可存取的已開／已關卡，記錄是否能重現、可能關聯及證據。查不到 codebase 不阻止通報。
4. 區分實作缺陷、需求歧義、刻意改行為與環境問題；需要產品判斷的差異交給使用者，假設不當根因。
5. 產通報草稿，清楚指出原情境修好後應看到什麼。複數獨立問題建議分開，但不擅自發布額外卡片。
6. 開卡由工具處理 repo／labels／Board，提出者不填通報 repo 或修復 repo。修復位置不明則保留中央入口分流，不亂猜子 repo。
7. 開發後沿用原情境驗收。邏輯 bug 先有失敗 regression test；純 UI／CSS 用可重現操作及前後畫面。部署、回歸證據由開發補，提出者只需確認使用結果。

## 5. 輸出內容與文件量

### 一般需求：一份 PRD

```markdown
# <要改善的功能>

## 問題與目標
誰遇到什麼問題，希望改善成什麼樣子。
本次包含／不包含。

## 現況與改動
現在怎麼做、預期改成什麼、影響與待確認。
現況是否已查核；未查核明列。

## 操作流程
入口與前置狀態：
1. 使用者…… → 系統…… → 下一步……
2. 使用者…… → 系統…… → 完成……
設計／畫面對照（有再附）。

## 規則與例外
已確認的規則、適用錯誤／空資料／權限等情境。
尚待確認的建議與問題。

## 驗收條件
AC-01：在……情況下，操作……，應看到……。
AC-02：……
```

小改動可直接放 Issue；大型需求可用 PRD 內的功能章節或子 PRD 組織內容，不新增 FRD 文件類型。已有文件則沿用，不為了標準化重寫一套。

### Bug：一份通報

```markdown
# <問題摘要>
發生位置／情境：
操作步驟：
實際結果：
預期結果（不確定可註明）：
截圖／影片／錯誤文字（有再附）：
影響與發生頻率（已知才填）：

## 查核補充（skill 後補）
相關需求、已知現況、是否重現、待查事項。
```

技術約束、repo、契約來源、revision 與 gate 證據不放提出者填寫區。開發交接時補技術附錄，中央卡／子卡直接引用同版 AC，不自行翻譯成不同標準。

## 7. 權限與失敗情況

- 只整理需求不遠端發布；已授權開卡則沿用授權，不重問。驗證 repo／查重／內容完整後以 body-file 或結構化工具發布並回讀。
- 需求確認不自動設 Ready；現有 Ready 可能觸發派工，需獨立開發授權與當下程式檢查。
- 發布一部分成功時保存 URL 與待補步驟，只重試未完成部分；timeout 先查是否已建立。
- 私有文件依可用 connector 與存取權讀取，不送公開搜尋；截圖／logs 去敏。不因協作方便而自動公開分享。
- 來源不可讀則回傳具體限制，保留草稿及待查項目；不要求提出者處理工程環境或提供 secrets。
- PRD／FRD 的使用者修改是新輸入；與前版決策衝突時列差異確認，不悄悄覆蓋。

## 8. 試跑與驗收案例

採固定匿名化情境與小型 codebase fixtures，先本地／唯讀試跑，不建立真實卡片。用獨立情境輸出評估，不能只檢查標題與關鍵字。

| 輸入／前提 | 預期行為 |
|---|---|
| 「共同挑戰很亂」，無法定位頁面 | 問產品情境，最多一兩題；不問 repo、不生成假規則 |
| 想新增現有功能 | 查到後說明現況，釐清差異，不照抄一份新增需求 |
| 明確希望改變既有預設 | 揭露影響，保留新意圖，不因現況不同否決 |
| 個人／探索頁混淆，參考 #184 | 草稿分入口、角色、資料與流程，AC 不混用 |
| 只有錯誤圖片，無固定重現 | 如實整理，補問操作，允許通報，不猜根因 |
| 無 codebase／文件權限 | 草稿註明未查核與下一步，不宣稱可開發 |
| 只有 route／service／page 檔案 | 不聲稱已部署或已上線 |
| 只有 prototype／開發分支 | 解析固定版本及適當 base；區分原型與現況、真實行為與 stub，不強迫補三份文件 |
| 舊 FRD＋新版分支有衝突 | 指出具體 FR／TP 差異並確認，不能默認新版分支全部正確 |
| FR／TP 已存在且兩份文件有相同短 ID | 用文件 ID＋原始 FR／TP 識別，不重編全部 AC，也不合併不同文件的同名 TP |
| 既有 PRD，使用者只改一項 | 保留其他決策與 ID，指出影響及需重驗項目 |
| 簡單功能／大型多流程需求 | 統一 PRD，後者按功能分章或子 PRD，不額外產 FRD |
| 只要草稿／已授權發布／部分發布失敗 | 分別驗證無遠端寫入、直接按授權完成、去重重試 |

格式與本地連結檢查後，再以 Claude／Codex 各測至少需求、bug、既有文件三種入口。無實際客戶端測試則標未驗證，不宣稱雙端可用。試跑記錄提問負擔、AI 擅自定案、現況誤判及缺漏，不為追求少問而省略決策。

## 9. 推進順序

1. 重整 PRD template＋prd-generation＋product-status-check，讓一個想法能形成經查核的需求草稿。
2. 補 bug template＋file-bug-issue，沿用共同查核與 gh-card 發布規則。
3. 加 Codex 入口、整理引用與使用說明，驗證案例與客戶端發現。
4. 以真實需求小批試跑；依授權發布模板與 skills，同步回讀遠端，讓團隊能取得相同版本。

需求與 bug 的整理／確認是本計畫的交付；新建自動化 runner、即時雙向同步、整套 gate 改造與模型選型不納入本輪。原 benchmark 的薄 spec＋厚 gate 原則保留，但不把尚未實作的驗證能力當作現有功能。
