# PM、設計師、RD 共用需求模板與 bug 流程規劃

日期：2026-09-13。狀態：規劃草案，待帶入使用者工作上的範例與團隊工具習慣。

本次完成本地模板、skill 與派工入口盤點，提出欄位、責任、交接與導入驗收。尚未修改正式模板／skill、建立遠端卡片或啟動開發。現有未提交修改保持原狀。

2026-09-13 補充：參考 harness benchmark 後，具體欄位以[模板 v2 建議稿](2026-09-13-template-v2-proposal.md)為後續試填版本；採薄核心與條件式附錄，保留 AC／決策／必要約束，先補驗證再精簡 OpenSpec。

使用者後續確認：需求與驗收通常為同一角色，模板不填固定負責人；「需求、開發、驗收」是流程階段，任務指派使用 Issue Assignees。產品與設計共同歸入需求。下文角色分工作協作參考，不要求重填人員或獨立設計簽核；實際欄位以 v2 建議稿為準。

## 1. 目標與設計原則

讓 PM、設計師與 RD 在同一份需求上協作，開發前知道哪些事已決定，開發中知道缺漏由誰決定，交付時知道如何驗收。需求不可能一次窮盡；流程要能提早發現缺漏，也能管理後續變更。

- 所有人都能手動填模板；skill 負責整理、提示缺漏與產生草稿，不是使用文件的前提。
- 同一需求保留穩定 AC ID；設計、子任務、測試與驗收引用同一條件。
- 欄位按提出、Ready、交付分階段補齊；不要求提出者先懂 API、SHA 或 OpenSpec。
- 未知、假設、已確認分開記錄。未知有責任人與下一步，AI 不把推測補成產品決策。
- 小改動使用精簡入口；跨 repo、複雜規則或資料變更按影響增加附錄。

## 3. 三個角色共用的協作方式

| 階段 | PM | 設計師 | RD | 交接產物 |
|---|---|---|---|---|
| 提出 | 問題、對象、目標、範圍、優先原因 | 補使用情境與目前體驗 | 指出既有能力與明顯限制 | 可追蹤的需求草稿與未知清單 |
| 細化 | 決定商業規則、例外與 AC | 操作流程、畫面狀態、文案、裝置行為 | 可行性、資料／API、依賴與風險 | 同一份需求及設計／規則對照 |
| Ready review | 確認範圍與產品驗收 | 確認設計涵蓋 AC 或合理 N/A | 確認可實作、依賴、測試方式 | 三方具名確認的版本、無阻擋問題 |
| 開發 | 回答產品決策與範圍變動 | 回答互動、文案與視覺差異 | 回報缺漏、影響、選項與驗證 | 決策紀錄、更新版本與受影響 AC |
| 驗收／發布 | 依 AC 驗收使用者結果 | 檢查適用畫面與互動 | 提供受驗版本、證據與部署結果 | 驗收結論及符合 Done 的交付 |

每項決策只有一位主要負責人；其他角色列為協作者。角色可由同一人兼任，但 AI 多角色檢視不算三方簽核。團隊沒有 QA 時，仍明列驗收者與測試責任，不讓驗收工作消失。

工具暫沿用既有提案：GitHub 管狀態與任務，Google Docs 可作討論入口，設計來源可用 Figma／POC，Markdown／OpenSpec 保存核准執行版本。實際工具待使用者確認；本次不新增平台依賴。

「同步使用」先定義為同一需求版本、同一 AC 與清楚更新責任。跨工具即時雙向同步另屬工程工作，現有模板不具備此能力。討論更新由需求 owner 彙整，Ready 時凍結；子卡與驗收只引用該版本，遇到衝突先回決策紀錄釐清。

## 4. 需求模板 v2：逐階段填寫

### A. 提出時的精簡入口

1. 標題、提出者、需求 owner。
2. 誰在什麼情境遇到什麼問題；目前怎麼處理。
3. 預期改善與可觀察結果；已知證據或範例。
4. 本次包含／不包含，以及優先原因或時間限制。
5. 已有文件／設計連結（沒有可填尚無）。
6. 未知與待決策事項。

可先建 Todo；技術 repo 未知時由分流者補齊，不要求 PM 猜答案。

### B. Ready 前共同補齊

| 區塊 | 必要內容 | 主責 |
|---|---|---|
| 流程 | 入口、前置條件、主要步驟、完成出口、返回／取消／中斷後行為 | PM＋設計師 |
| 規則 | 欄位含義、必填、預設、限制、格式、錯誤文案；角色與資料可見範圍 | PM，RD 檢查可行性 |
| 狀態 | 適用的成功、loading、空資料、錯誤、無權限、重複送出與重試 | 設計師＋RD |
| 設計 | 明確 frame／畫面位置、指定版本、對應 AC、互動與必要裝置／語系 | 設計師 |
| AC | 穩定 ID、Given／When／Then、可觀察結果、驗收方法與驗收者 | PM，三方檢查 |
| 技術影響 | 涉及 repo、資料讀寫、API 契約、既有資料、相容性、依賴順序 | RD |
| 交付 | 確認測試環境、測試資料、發布與回復安排、Done 定義 | RD＋PM |
| 決策 | 問題 ID、選項、影響 AC、負責人、期限、是否阻擋、結論與日期 | 各決策 owner |

按適用性補充：搜尋的排序／分頁，日期的時區，通知的觸發／重複／退訂，AI 的無結果／失敗／品質門檻，資料更動的回填／migration，外部服務的逾時。這些是情境檢查，不強迫每張需求填完整領域清單；N/A 記錄理由。

共用追蹤表建議：

| AC ID | 需求行為 | 設計 frame／狀態 | 規則 ID | 負責 repo／子卡 | 驗收方法 | 證據 |
|---|---|---|---|---|---|---|
| AC-01 | 已確認的可觀察結果 | 指定版本或 N/A 理由 | RULE-01 | 分工後補 | 人工操作／測試 | 交付時補 |

### C. 開發與交付才補的資訊

PR、base/head SHA、run、技術測試結果、截圖、真實 API 回讀、部署／smoke 與簽核沿用既有驗收模板。摘要先呈現結果與操作方式，技術明細在附錄。額度、lease、fencing token 等留在適用的自動化附錄，不成為一般需求提出的門檻。

### Ready 條件

- 每個範圍內行為都有可驗收結果；設計與 AC 無未解衝突。
- 會影響本次實作／驗收的問題已決定；非阻擋項有 owner、理由與期限。
- 適用的技術依賴與驗收方式明確；三方確認記錄綁定版本。
- Ready review 通過不等於已授權自動派工；Board 狀態的操作仍依既有授權與派工檢查。

## 5. 實作中發現缺漏的處理

| 情況 | 做法 | 決策責任 |
|---|---|---|
| 實作不符既有 AC | 當缺陷修復；保留原標準與回歸證據 | RD，原驗收者確認 |
| 規格未寫或有歧義 | 記錄問題、選項、影響與阻擋範圍；確認後更新規格 | PM 決定產品行為，設計師決定互動，RD 決定技術細節 |
| 新增需求或改變原行為 | 列出範圍／時程／設計／測試影響，決定本次納入或另開後續需求 | PM 協調，受影響角色重新確認 |

只暫停依賴未決問題的部分，其他已確認工作可繼續。影響既有 AC 就升版，記錄差異、受影響任務與重驗項目；不允許在 PR 或聊天中改完卻不更新契約。需求刪除保留歷史，不重用原 AC ID。

## 6. Bug 模板與 skill

### 通報者入口：PM、設計師、RD 都可使用

- 摘要：在何處做什麼，出現什麼異常。
- 預期結果、實際結果；若預期尚有爭議，標為待確認並引用設計／AC。
- 操作步驟與前置狀態；無法穩定重現可照實通報。
- 發生時間、環境／裝置／瀏覽器／已知版本；未知可留待調查。
- 影響哪些人／流程、發生頻率、是否阻擋、是否有暫時替代方式。
- 去敏截圖、錄影或錯誤文字；不要求非工程提出者找 log、根因或程式檔。

### 分流與修復階段

- 查重（含已關閉）並記錄相關需求／AC；區分缺陷、設計疑問、需求變更、環境／資料問題或待調查。
- 嚴重度描述影響，優先級描述處理順序；由 triage owner 判定並記理由，不假設 Board 已有 S/P 等選項。
- 記錄通報位置與實際修復 repo、負責人、受影響版本。repo 不明可留草稿／Todo 分流，不亂開子卡。
- RD 補重現結果、去敏 logs、已嘗試方案、根因假設與證據；假設不可當確認根因。
- 修復 AC 至少包含原情境及相鄰受影響行為。邏輯 bug 先有失敗 regression test；純 UI／CSS 用操作與修復前後瀏覽器證據，沿用現有 Issue 規範。
- 同一問題仍失敗可重開原卡；不同根因／新行為另卡關聯。無法重現不直接視為已修復。
- 關單要有修復版本、重驗結果、驗收者與適用部署證據；重複／不處理需寫結案原因。

skill 預設先產本地草稿與缺項；發布沿用當次授權，完成去重與 repo／label 檢查，使用結構化參數或 body-file，最後回讀。部分成功保存已建 URL，只重試未完成步驟。開卡不得默認 Ready 或啟動開發。

## 8. 導入步驟與驗收

1. **工作範例對照**：帶入使用者覺得好的需求／bug 模式，逐欄決定保留、調整或不採用及原因；確認日常工具與決策 owner。
2. **模板試填**：以一個 UI＋API 功能、一個純後端小需求、一個視覺 bug、一個偶發邏輯 bug 試填草稿。PM／設計師不需寫技術欄位就能提出，RD 能辨認開工阻擋項。
3. **Skill 對齊**：調整上述 canonical skills 與入口，保留人工填寫使用方式；既有模板未填完的卡不批次升版，新卡先採用，進行中的卡只補阻擋缺項。
4. **驗證相容性**：確認 OpenSpec／Parent parser、既有 dispatch 格式與 links；新增欄位檢查邏輯才加對應測試。Skill 用情境演練檢查，不能只檢查 Markdown 欄位存在。
5. **小批試跑與回顧**：使用三至五張實際卡，記錄每張補問次數、開工後規格變更原因、重工原因、填寫成本與驗收退回原因；先建立基線再訂改善目標。

必要情境驗收：

- 只有一句話的需求能留存草稿／Todo，附 owner 與未知，不捏造細節。
- 設計只有成功畫面時，指出適用狀態缺漏；不默認 Ready。
- 跨 repo 子卡沿用中央 AC，缺少依賴可被指出；不另造驗收標準。
- 純後端需求可合理 N/A UI，不要求假設計稿；未開始不要求 SHA。
- PM 通報「按鈕沒反應」可進分流，不要求先找根因；敏感證據不原樣發布。
- 開發中新需求能記錄改版及重驗範圍，不能直接覆蓋原規格。
- 僅要求規劃／草稿時沒有遠端寫入；發布失敗重試不重複建立。
- 測試通過但尚未部署時呈現實際階段，不冒充已上線／Done。
