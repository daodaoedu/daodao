# 共用需求與 Bug 模板 v2 建議稿

狀態：可試填草稿，尚未替換正式模板或 skill。承接[流程規劃與 GitHub 盤點](2026-09-13-shared-requirements-and-bug-workflow.md)，參考 [Harness-Governed Generation benchmark](../research/harness-governed-generation-benchmark.md) §7.3–7.7。

## 1. 採用方式

最新確認：提出者描述問題，skill 查核相關 codebase、起草，再集中確認一兩個關鍵差異。下方模板是整理產物，不是必須逐步填寫的空白問卷。保留 PRD／FRD：PRD 管問題、目標與範圍；FRD 管現況與改動、操作流程、規則／例外、設計與 AC。小需求可同檔分區；既有文件引用與補充，不新增重複規格。技術約束與驗收報告分別引用此基準。

**共同需求寫清楚決策與行為；RD 附錄只補必要約束；驗收用證據核對同一份契約。**

採納研究的薄 spec＋厚 gate、決策紀錄、按 repo／風險補驗證與有限修補迴圈。不以文件行數為硬限制，不刪除唯一的 AC 或跨 repo API 契約。研究 §7.3 曾建議移除 API／驗收細節，§7.4 隨後指出 gate 尚接不住；本提案以後者的前提為準。

研究以一人團隊為部分簡化前提；本次目標是 PM、設計師、RD 共用，因此保留具名決策與版本確認。研究中的模型數據、測試數量、外部案例與 gate 覆蓋率未在本次重新驗證，不作為已可刪文件的證據。

日常只提供兩個填寫入口：**功能需求**和 **Bug 通報**。兩者最後都引用相同驗收紀錄。RD 約束與決策先放同一文件，內容變大才抽成 `design.md`／`decisions.md`，引用而不複製。

流程分為「需求、開發、驗收」，不設固定負責人欄位。需求與驗收通常由同一角色處理；任務指派使用 Issue Assignees，不在模板重填。下文 PM／設計師為協作方式說明，不增加必填角色或獨立簽核。只有待決問題需要轉交時才註明由誰接續處理。

提出者入口只收問題、使用情境、預期結果、已知規則與設計／證據。不得要求提出者知道 repo、API、技術根因、OpenSpec 或執行版本；技術附錄與分流紀錄由開發／skill 接手時另行補充，不整份展示成提出者必填表單。

## 2. 功能需求模板（可直接複製）

```markdown
# <需求名稱>

階段：提出／細化／可開發／驗收中／完成（文件語意，非自動改 Board）
Issue：<建立後補>｜版本：<v1 草稿>｜來源：<FRD／POC 指定版本>

## 1. 問題與範圍 — PM
誰在什麼情境遇到什麼問題：
完成後可觀察的改善：
本次包含：
本次不包含：
優先原因／限制：

## 2. 場景與設計 — PM＋設計師
| 場景 ID | 頁面／入口 | 角色與資料範圍 | 操作與結果 | 設計檔／frame／版本 |
|---|---|---|---|---|
| SC-01 | | | | |

適用狀態：成功、載入中、空資料、錯誤、無權限、取消／重試。
逐項標明對應場景與預期行為；不適用寫理由。
適用裝置／語系／文案來源：

## 3. 決策與驗收條件 — 需求／開發／驗收共同確認
| 決策 ID | 規則與理由 | 決策人／日期 | 對應 AC |
|---|---|---|---|
| D-01 | | | AC-01 |

| AC ID | 場景 | Given 前提／資料 | When 操作 | Then 可觀察結果 | 驗收方式 |
|---|---|---|---|---|---|
| AC-01 | SC-01 | | | | |

## 4. 待確認與變更
| 問題 ID | 問題／選項 | 影響 AC | 是否阻擋本次開發 | 負責人／下一步／期限 |
|---|---|---|---|---|
| Q-01 | | | | |

版本變更：<差異、理由、影響 AC、確認人與日期、需重驗範圍；首次填 none>
開工確認：<需求與開發確認範圍，驗收方式已明確>
```

提出時只需問題、預期改善與已知範圍；其餘標待確認即可。Ready 前才要求適用場景、決策、AC、依賴與驗收方式完整。每張卡的必要條件均需通過；若部分要延後，明確移出本次範圍並保留歷史，不把失敗 AC 改成選填。

不要再獨立寫一份與場景／AC 重複的 User Story 長篇；需要時放在問題描述即可。驗收條件保留穩定 ID，子卡不另造同義 AC。

### #184 的試填示範（示意，尚未取得產品確認）

| 場景 | 應先問清楚的內容 | 不能讓 AI 自行決定的部分 |
|---|---|---|
| 探索共同挑戰 | 入口、可見對象、篩選、卡片操作、對應 POC | 是否顯示已加入／已結束項目、公開範圍 |
| 我的共同挑戰 | 入口、與目前使用者的關係、進度、卡片操作、對應 POC | 哪些參與狀態會列入、何時顯示打卡按鈕 |

例如 `AC-01` 草稿可寫：「Given 使用者符合 D-01 定義的參與資格，When 開啟『我的共同挑戰』，Then 僅列出符合 D-01 的項目。」但 D-01 必須先確定，並準備符合與不符合的資料；這條草稿尚不能進 Ready。這樣能直接抓出原本混在一起的兩個頁面。

## 3. RD 技術與驗證附錄（按影響填）

```markdown
## 技術影響與必守約束 — RD
涉及 repo／子任務／相依與發布順序：
既有能力與核對證據：<程式存在、測試、部署、實際可用分開記錄>
API／資料契約來源：<跨 repo 必填來源與版本；無影響可 N/A>

| 約束 ID | 必須成立的條件／理由 | 對應 D／AC | 驗證方式 | 目前限制 |
|---|---|---|---|---|
| C-01 | | | | |

適用項：交易原子性、權限／禁止曝露的欄位、狀態轉換、資料相容性、migration／回復。
共用架構規則引用 repo 規範；本次只列新增或例外約束。

| D／AC／C | 檢查或操作 | 能證明什麼 | 無法涵蓋什麼／人工補驗 | 負責人 |
|---|---|---|---|---|
| AC-01 | | | | |

Done：<必要測試、產品／設計驗收、合併、部署與 smoke；不適用有理由>
```

不複製可由 canonical schema／程式產出的 SQL、Zod 與 OpenAPI 全文；但保留契約來源、版本、關鍵限制與測試。沒有可靠契約來源時先補契約，不能以「之後 gate 會檢查」略過。從實作生成的 schema 再驗同一實作，不能獨自證明它符合產品需求。

「厚 gate」落在可執行驗證與可信 CI，不是讓 PM 多填欄位。自動化另有執行附錄記錄 run、SHA、版本與額度；共同需求首頁不要求這些。

## 4. Bug 模板（可直接複製）

```markdown
# <在哪裡做什麼，發生什麼異常>

## 通報 — 任何角色都能填
發生頁面／入口：
操作與前置狀態：<無法穩定重現也可照實填>
預期結果：<依據 AC／設計；未定義則標待確認>
實際結果：
環境／裝置／版本／發生時間：<知道多少填多少>
影響與頻率／替代方式：
證據：<去敏截圖、錄影或錯誤原文>

## 分流 — triage owner 補
類型：缺陷／需求疑問／新增需求／環境問題／待調查
相關需求／AC／重複卡：
影響程度／處理優先與理由：
缺少資訊與下一步：

## 修復與驗收 — RD＋驗收者補
重現結果／根因證據：<假設與確認分開>
| 修復 AC | 原情境與預期結果 | 回歸範圍 | 測試／人工步驟 |
|---|---|---|---|
| BUG-AC-01 | | | |
修復版本／PR：
重驗結果與證據：
適用部署／smoke／驗收者：
結案原因：已修復／重複／不處理（寫明依據）；仍失敗則重開或持續調查。
```

「分流」與「修復與驗收」是接手後追加的紀錄，不放入通報者初始表單。Issue 所在 repo 由工具取得，修復範圍由開發查核，跨 repo 時再建立必要關聯。

純 UI／CSS 以操作與修復前後瀏覽器證據驗證；邏輯 bug 先建立會失敗的 regression test 再修復。不要要求提出者先寫根因；不要把修改任何 test 一律禁止，應阻擋未經說明地弱化既有預期，允許補測試及修正已證實錯誤的測試。

## 5. 共用驗收紀錄

沿用 `acceptance-report.md`，首頁只需：

| 項目 ID（AC／C） | 預期 | 實際結果 | pass／fail／blocked／not-run／n/a | 本版本證據 |
|---|---|---|---|---|
| AC-01 | | | | |

再列受驗版本／環境、未完成項目、產品與設計結論、部署結果。詳細 run／SHA／manifest 放附錄。人工 review 意見與腳本測試結果分開；沒有跑的 gate 不填 pass。核准綁定需求及受驗版本，變更後重驗受影響項目。

## 6. Skill 應做的工作

1. **整理**：從對話／文件抽取已知資訊，標出來源；未知與建議不能冒充已確認決策。
2. **按影響補洞**：找缺少的角色、場景、資料範圍、例外與驗證方法；每次集中詢問最影響 Ready 的少量問題。
3. **檢查 Ready**：產出「可開發／仍缺哪些決策、由誰補」；AI 審查不替代產品或設計確認，也不自行切 Board Ready。
4. **交接**：凍結同一版 AC／D／C，子任務引用；auditor 同時取得行為、產品決策及必要約束，不只看 diff。
5. **驗收與變更**：結果指向證據；重複失敗依既有兩次上限交由人判斷原因，不自動降低 AC，也不把重複 finding 直接認定誤判。

維持 `prd-generation`、`gh-card`、`file-bug-issue` 的既有入口，模板是唯一欄位來源。增加非工程使用者的 GitHub Issue Form 可作後續交付，讓手動與 skill 產出的語意一致；不要求每位使用者安裝 agent。

## 7. 實施順序與不能跳過的條件

1. 先用 #184／#190 匿名化情境試填以上兩種入口，三方確認容易填且能暴露缺漏。
2. 修改共用模板與三個入口 skill；先保留現有 OpenSpec 格式。當前 `bin/pipeline/dispatch.ts` 明確要求有效 `tasks.md` 並依章節拆卡，不能直接刪掉改用 `decisions.md`。
3. 列出每項要精簡的內容由哪個可信驗證接手；只移除重複內容，未被覆蓋的約束繼續保留。不因某 repo 有很多 tests、改動少或被稱為「config-only」就視為足夠。
4. 以固定案例評估 skill：雙頁混淆、只有截圖的 bug、純後端 N/A、跨 repo 依賴、未核准變更、測試通過但未部署、只要草稿不可發布。檢查實際輸出／工具行為，不只檢查欄位名稱。
5. gate 與 dispatch 相容性改造另立工程工作，驗證後才逐步簡化 OpenSpec。研究提案、prompt 規則、已安裝 hook、已執行測試、CI 強制 gate 是不同成熟度，不互相代稱。

模板成功的標準是三方能用同一份內容回答「做什麼、哪裡未定、怎麼驗」，並降低因未記錄決策造成的重工；不是填滿所有格子或壓到指定行數。
