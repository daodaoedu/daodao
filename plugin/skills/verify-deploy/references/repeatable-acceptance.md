# 可重複的驗收步驟與資料

適用於包含取消／確認、刪除等會消耗資料的分支，或要求手機／參考稿比對的網頁驗收。工程在交接前準備，PM 在操作前核對；不新增原 AC 沒要求的測試，也不擴大任何寫入授權。

## 工程交接前

把同一 AC 的不同分支分成獨立編號步驟：例如「AC4／取消後仍存在」與「AC4／確認刪除後消失」。沿用原 AC，不新增 AC 編號。每一步只交付一個能獨立判定的結果；捲到底、關閉等操作若有各自預期，亦分列觀察。

需要消耗資料時，先規劃可重來的資料：

- 取消與確認刪除使用兩筆專用資料，分別給直接連結，確認擁有者、角色與必要狀態一致；不要把原有資料拿來當替代品。
- 無法提供獨立資料時，先實跑可用的重設方式並寫明何時、由誰重設；重設前仍能完成取消分支，且不會使其他必測項失去資料，才可交驗。只有「請工程重建」而沒有可執行方式不算準備完成。
- 把不依賴刪除的閱讀、取消、桌面／手機驗證排在確認刪除前；真的依賴刪除的後續步驟，明寫其相依關係及使用的資料。
- 自動開信、一次性邀請、期限等也會改變前提，列明消耗後怎麼重來；不要只檢查 DELETE。

在交接「工程證據」記錄以下資料表，PM 步驟仍只放畫面操作：

| 原步驟／AC 與分支 | 專用資料連結／擁有者 | 初始狀態與相依步驟 | 保存／到期與重設方式 |
|---|---|---|---|
| 3／AC4 取消 | 專用 A／指定 PM 帳號 | 未送達，取消後仍存在 | 保留至驗完；工程重設腳本與執行方式 |
| 最後一步／AC4 確認刪除 | 專用 B／同帳號 | 未送達；先完成所有用到 B 的觀察 | 可消耗；重跑前用已驗證腳本補回 |

### 重設方式的交付

需工程重設時，把腳本、fixture manifest 與執行命令留在任務目錄，交接附工程可取用的位置與最近一次執行／回讀證據，不讓 PM 跑 shell 或 API。只描述如何重建而沒有實跑，不能寫「可重複驗收」。

腳本依任務既有授權操作：鎖定 dev 與明列的 fixture ID，寫入前核對擁有者及可接受的前狀態；不符合就停止，不擴大到整個帳號。不得重設原有資料或為補驗新增通知排程／寄信。重複執行應回到相同資料前提；完成後核對目標狀態、排程及其他資料未變。找不到原 fixture 時，依 manifest 建立合成專用資料或明確報錯，不從其他信件複製私人內容。資料已通過的狀態無需為補驗全部回退。

## 尺寸與視覺比對

手機／響應式步驟寫清楚 **寬×高 CSS px**，例如「手機 390×866」；桌面亦標明自己的尺寸，不能拿桌面數字充當手機尺寸。若用實機，交接附實測 viewport。尺寸寫在對應驗收步驟，不能只藏在工程報告中。來源只要求手機、未指定尺寸時，由工程採用 **390×844 CSS px**，先以該尺寸實跑並確認實際 viewport，再把尺寸寫入每個手機編號步驟；這是測試環境補齊，不需要 PM 另選尺寸。來源已有尺寸時沿用來源；有多頁時逐頁寫明適用尺寸。不得只寫「手機版」「手機寬度」便交驗。

要求符合參考稿時，提供可開啟的參考連結或已保存的對照圖，列出要看的項目（如彈窗寬度、底色、遮罩、關閉鈕與文字區），以及已確認的差異。數值比對由工程量測，PM 看畫面；不同內文或語系的高度差不能直接拿來判像素一致。同內容精準量測仍依 [poc-compare.md](../../develop/references/poc-compare.md) 執行。

## PM 操作與證據

第一個測試操作前，把全部必測分支存成 test-acceptance §6 指定證據目錄內的一份檢查表，保留原步驟／AC、資料、依賴與預期。每一分支的結果獨立記錄；多個分支共用 AC，不代表可以合成一列 PASS。

| 原步驟／AC 與分支 | 資料連結 | 預期 | 實際／證據檔 | 結果 |
|---|---|---|---|---|
| 3／AC4 取消 | 專用 A | 取消後重開仍存在 | 尚未執行 | 未執行 |
| 最後一步／AC4 確認刪除 | 專用 B | 確認後節點消失 | 尚未執行 | 未執行 |

- 每完成一分支，立即把觀察與證據路徑寫入同一份表，結束時據此產生報告，不憑記憶補填。
- **執行確認刪除或其他會使前提消失的操作前**，重查該筆資料所有需保留的閱讀／取消／尺寸等前置觀察，確認已實測並存證；有缺項先完成，受阻就停下該破壞性操作，繼續其他獨立項目。此檢查不取代現有工具的確認要求。
- 指定尺寸後先確認實際 viewport，再操作／截圖；視覺比對逐項記錄「參考值或畫面 → 實際觀察」。無法設定尺寸或開參考稿時，只標受影響項 BLOCKED，不宣稱已比對。
- 漏驗後資料已被消耗：記明漏掉哪個分支、哪筆資料及最後操作，請工程只補相應專用資料。已通過項目可以引用原報告，但不能用另一分支成功或舊工程證據補成當次 PASS。

`acceptance-lint` 的 `mobile-viewport-missing` 會擋下手機／響應式編號步驟缺寬高的交接；尺寸須寫在同一編號步驟，不借用桌面或工程證據段。

格式 lint 只能檢查可辨識的文字缺項，不能證明 fixture 獨立、操作順序遵守或畫面實際完成；上述前置檢查與逐項證據仍需實跑。


## 使用最新交接檢查

共享 root 可能停在舊文件分支。#471 曾從舊 root 執行沒有手機尺寸規則的 linter，即使 `origin/main` 已合併 #469，仍回報 OK。每次發交接前先 fetch main，再從該 revision 的乾淨隔離 worktree 執行 linter；不要切換、pull 或 reset 共享 root。保存 gate revision、命令與結果，不能用舊 checkout 的 OK 代替。

在 daodao root 執行（`comment_file` 使用留言檔絕對路徑）：

```bash
(
set -e   # 任一步失敗即停止，不會繼續放行
comment_file=/absolute/path/acceptance-comment.md
git fetch origin main
gate_dir=$(mktemp -d /tmp/daodao-acceptance-gate.XXXXXX)
git worktree add --detach "$gate_dir" origin/main
git -C "$gate_dir" rev-parse HEAD
pnpm -s exec tsx "$gate_dir/bin/pipeline/acceptance-lint.ts" "$comment_file"
# 有 error 先改留言再以同一 gate 重跑；通過並保存結果後才發布及清理
git worktree remove "$gate_dir"
)
```

fetch／建立隔離 worktree／linter 任一失敗，就保留未交驗並排除工程前提，不改用舊 gate 放行。此檢查只驗文字；仍須同帳號、同資料、同尺寸實跑並還原。
