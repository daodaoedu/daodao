# 共用驗證配方

`develop verify`、`verify-product`、`verify-deploy`、`test-acceptance` 共用這份準備、操作、證據與資料生命週期原則。各功能的入口／selector仍由 feature map 與既有 driver 維護，實際命令由原 skill 提供；這份配方不新增 driver、發布授權或另一套狀態機。

## 先選驗證目的

由呼叫的 skill 與本次任務決定目的，不靠目前登入者猜使用者角色。同一份工程結果不能重新貼標成正式 PM 結果。

| 呼叫入口 | 受驗範圍與身分 | 證據交付與完成 owner |
|---|---|---|
| develop verify | 任務 worktree、同版完整 AC、適用 API／UI／DB；依工程規則選帳號與工具 | 任務 evidence／矩陣及工程報告；`verified` 與發 PR 閘門仍由 develop 決定 |
| verify-product | 自己的隔離 runtime、已註冊 driver 或既有 harness；工程 session與外部邊界替換須明示 | driver action/result、artifact與清理；不代表 dev 部署或正式 PM 驗收 |
| verify-deploy | 已部署的指定 revision、dev正常／錯誤旅程、指定PM帳號與相同資料的工程重播 | 凍結交接、lint／前置檢查／closeout、還原保留資料；發布／移 Acceptance 依 verify-deploy |
| test-acceptance | dev最新請驗收留言，指定PM測試帳號、Google與正式發布身分 | 依該 skill 的能力檢查選擇工具與附件路徑，暫存／回讀／清理依其 environment；判定與移卡仍由該 skill 主流程執行 |

PM瀏覽器與登入細則只由 test-acceptance 的 environment 維護；工程登入與環境替換只由 develop／verify-product維護。不能把工程 dev-login、localhost、資料庫或 shell 操作冒充 PM 的產品畫面步驟；同一自動化工具可供不同流程使用，仍須各自通過身分與能力檢查。工程使用者沒有 PM 工作階段時，保留 PM側待辦，不要求他代登入另一人的專用帳號。

## 準備同一份可執行契約

沿用原任務矩陣／交接清單即可，不強制每張卡新增 JSON 或第二份規格。對每個原 AC／步驟／分支確認：

| 項目 | 必要內容 |
|---|---|
| 來源 | 同版 AC／請驗收留言、原編號、輸入與預期；不自編需求或擴測範圍 |
| 環境 | 入口、語系、目標版本與 API target；本機、dev、替換／真實邊界分開 |
| 帳號與範圍 | 指定身份、完整角色、必要組織／場次、owner／coach等情境權限；預期與實際核對分開 |
| 資料 | 精確ID／連結、擁有者、必要欄位與數量、目前狀態、可重用／只讀／一次性、適用期限 |
| 順序 | 分支依賴、消耗前必須完成的觀察、獨立資料或安全重建方法 |
| 畫面條件 | 原來源要求的viewport／參考稿與要觀察的差異；純後端不加無關UI要求 |
| 副作用與收尾 | 本輪允許的寫入、通知／排程／模型呼叫，預期終態、還原／清理／保留責任與方法 |
| 證據通道 | 原skill指定的存放或直接交付方式，消耗／不可逆步驟前先確認必要證據能保全與交付；發布受阻與獨立非消耗觀察分開 |

取消／確認、資料消耗、手機尺寸、參考稿與重建細節只在 [可重複驗收](repeatable-acceptance.md) 維護。工程補尺寸與 PM不自行猜尺寸的責任分開；檢查表不改變原 skill 的證據存放政策。

## 執行與逐項記錄

1. **查目前前提**：確認真正受驗環境、版本、實際登入帳號／角色與資料，不以名稱、舊截圖或 registry 當即時保證。工程依原skill做 Doctor／actor／fixture檢查；PM從指定畫面確認，不要求PM跑工程API。缺前提先記受影響項，不能換錯帳號或降低預期求通過。
2. **操作原入口**：依同一契約實做每個原步驟，保存動作與實際終態。背景任務、DB／HTTP或直接service檢查各列自身範圍，不能代替沒有走過的畫面。缺 driver時依原入口找既有 harness；沒有可行recipe就記缺口，不假裝已接入。
3. **每個分支各記結果**：沿用原編號／AC，列輸入、預期、實際、時間／版本及證據。PM依自己的流程維持逐項檢查表並交付一則含圖報告；必要暫存及清理由其 environment 統一維護。工程沿用任務證據與driver result。
4. **狀態改變前再核對**：一次性操作前先完成依賴同資料的閱讀、取消、尺寸等觀察；缺項或前提漂移就停止受影響操作。正常提交後變consumed可能是預期，不自動重設PM答案或回滾正式結果。
5. **異常先分範圍**：記實際觀察與依賴關係；環境／帳號／資料受阻不直接判產品FAIL。是否需二次重現、何時可判PASS、如何處理BLOCKED，由原skill決定，不統一成一種判定標準。多個必要阻擋各有恢復證據，不能用部分修復稱全部解除。
6. **依生命週期收尾**：先留下判定所需證據，再執行下節適用的還原、保留或清理，最後回讀。未完成的必要收尾仍列未完成；不刪證據、不把未驗項移走湊全綠。

規格／版本或資料在操作中改變時，記下已測版本，停受影響部分並更新契約後重驗；不能把不同版本的通過子集合併成同一輪完整通過。無關步驟能否繼續由原流程與依賴決定。

## 證據邊界

各項實際紀錄source版本／環境、actor、入口、動作、觀察、artifact或已交付附件、替換與未驗項。資料儲存、背景副作用適用時，用可讀第二視角回讀；不要求純UI每一步查DB，也不把工程查核搬給PM。

| 證據 | 可支持的結論 | 不能替代 |
|---|---|---|
| 真畫面動作＋可見結果／實際HTTP | 該入口、角色與版本的行為 | 未走過的入口、GoogleOAuth、部署或正式PM判定 |
| worker／queue事件＋持久化 | 該job的處理與副作用 | 使用者能完成整個畫面流程；queue完成也不證明inbox實收 |
| 真SMTP進本機mailbox | 該SMTP邊界的內容／href | Gmail／Outlook inbox或spam placement |
| 邊界capture／mock／時間加速 | 明示替換情境的呼叫與結果 | 自然等待、真供應商或完整外部旅程 |
| unit／直接service測試 | 被測邏輯及覆蓋情境 | UI、自然排程或整條業務旅程 |
| lint／收據／格式gate | 缺項與證據綁定符合檢查 | 證據真偽、畫面已操作、發布／自動hook已啟用 |

需要登入卻停在登入牆，只能證明該入口受阻；成功建立session不證明Google登入。圖上只有終態、agent自述、mtime、cached畫面或HTML預覽，不能單獨證明動作與結果。截圖不得包含token、驗證碼、私人回答或無關個資。

工程證據、合併、部署、工程冒煙與正式PM結果各自保留。交付／移卡／關issue只依原入口的完成條件和既有授權；共用配方不新增寫GitHub、對外寄信或模型呼叫權限。

## 還原、保留與清理

| 本輪資料類型／目的 | 收尾動作 |
|---|---|
| 純唯讀觀察 | 記未建立／改動；有檢視次數等副作用則如實記錄，不為填「不變」逆改counter |
| 已獲授權可改的共享／既有資料 | 寫入前保存基準；依精確ID與允許欄位還原並回讀，不擴大到帳號／組織全部資料 |
| 工程交給PM的專用資料 | 還原為PM起點後再查前提，保留至驗完並列期限／可執行重建方式；不按一般冒煙清理把它刪掉 |
| 只供本輪工程冒煙的新資料／runtime | 依原skill清理owned排程來源、帳號或自有process，回讀結果；不啟停其他session，不按模糊名稱批次kill |
| PM合法操作完成的結果 | 照最新交接的收尾做，不自動刪除答案、撤回批准或重設已通過分支；未授權變更留結果與責任紀錄 |

還原／cleanup失敗時保存精確對象、原值、實際結果與下一步，不用「已執行腳本」當成功。已寄通知不能召回；停權也不保證讀權撤銷。這些不逆轉的副作用必須在紀錄中保留。

## 配方與防線維護

功能操作的來源仍是 feature map／driver；recipe只讀來源與可見結果，沒有source＋live證據不稱某driver已可重跑。工具漂移、前提漂移和產品FAIL分流修正，不用改文件或弱化預期掩蓋錯誤。

防止重犯沿用 `prevent-repeat-failures` 的[防線紀錄](../skills/prevent-repeat-failures/references/control-record.md)：來源、預防階段、拒絕條件／被保護動作、接入位置、反例／正常對照與實際狀態。不要在各驗證skill再維護一份同義gate表；既有agent-handoff／closeout契約仍用各自格式，引用紀錄而不自行更改schema。
